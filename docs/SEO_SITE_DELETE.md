# SEO 网站彻底删除（2026-10-11）

## 行为

网站仅提供启用、暂停状态，不再提供归档。0107 将历史 archived 转为 paused，不自动启用，不删除已有网站。管理表显示中文状态。

删除前弹出“删除网站及关联数据”确认，明确不可恢复及范围。确认后使用 tenant_id、site_id 和用户所确认的 canonical_domain；后端要求 seo.assets 编辑权限、客户模块访问权限、租户匹配，并锁定网站行。旧客户端缺少 confirm_domain 返回422，域名变化返回409。缺少0107删除触发器返回503，不会退化为仅删除网站并遗留关联数据。

网站及其数据库内 SEO 业务记录在同一事务内删除：人工消息、参与者、会话，随后固定的子表到父表清理清单。内容分发版本、发布记录、尝试等由既有外键级联清理；普通 site_id SET NULL 的表显式删除，避免变成无归属记录。清单与全部当前 SEO site_id 模型比对的测试可发现新增遗漏。

不会删除外部网站、撤回外部平台文章、取消已经送达供应商的请求；保留客户、用户、租户级共享分发连接及平台计量/费用记录。只清理数据库记录，不宣称物理擦除备份或磁盘中的截图/上传文件；失去记录的截图不可再经原业务接口访问，磁盘回收仍由存储维护负责。

保存网站或删除成功后通知工作区重新校验，避免刚启用的网站仍被旧状态切回。

## 数据库边界

新增迁移 `0107_seo_site_delete`，直接父版本 `0106_seo_content_messages`；没有改写历史迁移。

- `trg_seo_site_purge` 是 seo_sites 的 BEFORE DELETE 行级触发器。根网站行由后端 FOR UPDATE 锁定，外键关联插入在并发删除后失败；清理中任何错误回滚整个事务。
- `seo_purge_site_data()` 是 SECURITY DEFINER 触发函数，仅处理 OLD.tenant_id/OLD.id。全部表名在迁移时固定到实际 schema，search_path 固定 pg_catalog，无调用方可传入的动态SQL，PUBLIC EXECUTE撤销。生产函数应由受控迁移对象所有者持有；应用账号不应拥有表、函数、schema CREATE或TRIGGER权限。
- 应用账号仍只需已有 seo_sites SELECT/UPDATE/DELETE 权限，不授人工消息 DELETE 或确认记录 DELETE。整站入口的触发函数以对象所有者权限处理这些关联记录。
- 消息保护仅在嵌套深度2、当前消息所属客户及网站与该整站删除的事务上下文一致时放行 DELETE。普通 UPDATE/DELETE/TRUNCATE 仍被拒绝；伪造上下文后直接DELETE也被拒绝。
- 0107代码继续兼容0106运行；未升级时彻底删除关闭。健康检查接受0107，同时沿用0106结构检查。

## 上线步骤及回退

用户已于2026-10-11明确授权上线。按下列流程发布兼容代码、备份并单独执行0107迁移；验收不删除真实网站。实际执行结果另记发布记录。

发布前核对最新正式分支、生产数据库版本、迁移对象所有者和运行角色，备份待迁移库并保留兼容0106/0107的回退应用包。先部署兼容代码，再在单独批准的事务中执行0106→0107；普通部署工作流仍是 migration=not-run。不得直接回退到只认识0106的旧健康检查器。

迁移downgrade移除整站清理触发器，恢复消息只追加函数；已经删除的数据不能靠downgrade恢复，历史归档网站仍保持暂停。恢复误删数据需要备份恢复方案，不能宣称改代码就能恢复。
