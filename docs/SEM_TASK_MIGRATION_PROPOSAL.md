## 为什么不直接放进 migrations/versions

main 基线 e6a5185c750bd79b7eb25a096e0fa711db3b8311 的头是 0088；
SEO 锁定源码 4e83611aabc8c3d9bb6ecee1a6aff37a2fbfbe21 的头是 0094。
生产 0094、目标表及序列/索引不存在来自负责人转交的 2026-09-06 13:23 只读报告，
不是本任务直接连接生产测量。后续变更必须重新核对临执行状态。

同名 0087 在 main 指向 0085，在 SEO 指向 0086；0069 仅末尾空行不同。
SEO 还包含 main 缺少的 0081–0084、0086、0089–0094。
docs/SEO_IMAGE_ALT_EVIDENCE.md 记载了当时 promotion 对齐生产父节点的设计；
这解释源码差异，不证明历史执行内容。0093/0094 的实际执行入口仍无完整证据。

同一个 revision ID 的两种父节点不能在一个 Alembic 图中同时表达。
不能通过简单增加 merge revision、把两个目录同时配置为 version_locations 或改写旧 0087 解决。
也不能在 main 中直接注册缺少父节点的 0095，或从 main/SEM 旧头运行到 head。
因此本提案不改任何历史迁移，不注册新迁移，不影响现有 CI 迁移头及普通应用发布。

## 共享历史处置方案（已授权本地实现，生产执行仍未批准）

建议采用**独立、锁定的共享数据库迁移源包**，与 SEM/SEO 应用发布包分离：

1. 保留 main 历史迁移原样，明确它不是当前共享生产库的迁移执行源。
2. 以双方审核的 SEO 0094 完整迁移图作为独立源包候选，将每个历史文件按原始字节及 SHA-256
   保全并记录来源；不以当前源码冒充所有历史实际执行的证明，保留证据缺口记录。
3. 在该单独图中添加审核后的 0095 草案。其起点为经重新核验的生产单行 0094，
   审核计划必须只包含 0095；不能重新执行 0081–0094，也不能 stamp 或手工改版本表。
4. 本 PR 新增 `ops/sem-task-migration`：锁定源文件清单、构建/验包和仅限本地的验证入口。
   111 个历史迁移及 5 个必要辅助文件按来源提交原始字节校验，另加入候选 0095 和专用 env。
   不加入任何自动发布/迁移 workflow，不读取应用配置或 DATABASE_URL。
5. 本地实际 Alembic 已验证唯一头及只执行 0095 的路径；生产执行入口、权限、备份恢复及
   全库结构对账仍未验收。此源包仅供审核及本地演练，不得拿本地入口直接用于生产。

替代方案是由共享迁移负责人正式统一 main 的历史迁移源；由于涉及同名历史 revision 的
父节点冲突，不能在“不得改历史”的约束下由 SEM 窗口擅自替换文件。若不接受独立源包，
请先决定统一历史的治理方案，草案继续保持不注册。
